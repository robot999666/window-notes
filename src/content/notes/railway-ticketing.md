## 把一趟列车拆成区间

一条线路有多个停靠站。乘客从 A 站到 C 站，占用的是 A–B 和 B–C 两个区间，而不是这趟车在所有区间的座位。另一位乘客从 C 站到 D 站，可能使用同一座位的后续区间。阅读这个课程实验时，可以先把线路画成站点与边的关系，再理解余票为什么不能只用一个总数表示。

公开说明把余票计算精确到每一个站点区间。这意味着一次订票要检查经过的全部区间，确认它们都能够容纳这次出行，再修改相关余票。退票则沿着原订单释放对应占用。这里描述的是项目的业务模型，并不意味着它实现了铁路生产系统的全部规则。

## 三类数据如何联系起来

仓库把车次、乘客和票务分别组织成模块，对应 `train`、`passenger` 和 `ticket` 相关源码。阅读时，可以从一张订单反向追踪它引用的车次、日期、乘客和站点，观察这些信息怎样在界面操作与数据文件之间流转。

乘客身份校验使用姓名与证件号的组合，考虑了同名情况。姓名适合展示，却不能单独充当唯一身份。对于课程系统，理解这种区别比先增加复杂界面更有价值：哪些字段用于显示，哪些字段用于确认身份，哪些字段参与订单关联，应该分别看清楚。

## 从一次操作检查状态一致性

可以把下面的步骤作为阅读和自行验证的路线，而不是已完成的测试结果：

1. 先查询一个区间的余票，记录当前状态。
2. 创建经过这个区间的订单，观察订单与区间余票是否一起变化。
3. 查询一个不重叠的区间，检查它是否保持原有状态。
4. 退回原订单，观察占用是否被正确释放。
5. 重新启动程序，比较文件保存前后的数据是否一致。

这个顺序把“操作成功”的界面提示，转换为可以核对的数据变化。遇到异常时，再判断问题位于输入校验、业务更新还是文件读写，定位会更清楚。

## 文件与编码也属于实验的一部分

车次、乘客与订单通过文本文件保存。公开 README 还特别说明了 GB2312 源码编码与车次文件格式差异。打开源码或自行编译时，需要保持字符解释方式一致，否则中文乱码可能遮住本来正确的逻辑。

课程项目采用控制台交互，站点停靠、年份范围与边界情况存在自己的简化规则。公开说明中的“推测”也应保留为待核实事项。这里记录的是数据结构如何承接业务状态，而不是生产级票务服务的性能或安全结论。
